TRABALHO FINAL SOBRE PADRÕES DE PROJETO1

1. Contexto e objetivo
Design patterns são soluções reutilizáveis para problemas recorrentes de projeto, mas dominá-los exige mais
do que memorizar o catálogo GoF: é preciso saber quando um padrão se aplica, por que ele resolve o problema
e quais trade-offs ele introduz. Uma das formas mais profundas de aprender um conteúdo é ensiná-lo a outra
pessoa (learning by teaching).
Nesta tarefa, cada dupla projeta e implementa um sistema multiagente em Python que atua como um agente
pedagógico: um conjunto de agentes de IA que, trabalhando juntos, ensina um design pattern a um estudante
iniciante. O sistema é construído com um framework de orquestração de agentes e opera com um modelo de
linguagem local, sem nenhum custo de execução. Depois, todas as duplas interagem com os sistemas
construídos pelas outras duplas em sessões estruturadas em sala e avaliam a experiência.
Objetivos da tarefa:
 Aprofundar a compreensão conceitual e prática dos design patterns, porque projetar um sistema que
ensina um padrão exige dominá-lo com precisão.
 Aplicar, na prática, conceitos de engenharia de software já trabalhados na disciplina: arquitetura,
separação de responsabilidades, coesão, acoplamento e teste.
 Desenvolver a competência de interação crítica com IA, incluindo a capacidade de identificar respostas
imprecisas ou enganosas de modelos generativos.
 Exercitar a avaliação de artefatos de software por critérios objetivos, incluindo a avaliação de sistemas
construídos por terceiros.

Requisitos mínimos do sistema:
 Múltiplos agentes com papéis distintos, cada um com seu prompt de sistema (persona, objetivo e
regras), trabalhando de forma coordenada.
 Memória da conversa, para que o sistema seja capaz de conduzir um diálogo coerente com o
estudante ao longo de vários turnos.
 Lógica pedagógica explícita distribuída nos agentes: apresentação do conceito, exemplificação,
exercício, diagnóstico de erros/conceitos equivocados e feedback.
 Regras anti-alucinação: o sistema não pode inventar padrões, participantes, consequências ou
exemplos; quando não souber, deve dizer que não sabe.
 Tratamento básico de erros (entrada vazia, falha do modelo, saída inesperada).
4. CUSTO ZERO — regra obrigatória
É proibido, em qualquer hipótese, que o sistema dependa de API paga, de chave de API, de serviço em nuvem
ou de qualquer mecanismo que gere custo financeiro por uso. O trabalho final deve rodar inteiramente com o
modelo de linguagem executado na própria máquina da dupla, sugere-se o uso de Ollama.
 O modelo de linguagem deve ser baixado e executado localmente (modelos abertos quantizados).
 Sugestões por hardware: qwen2.5:7b (máquinas com 16 GB de RAM), qwen2.5:3b (máquinas com 8
GB de RAM). Modelos menores são aceitáveis se a qualidade pedagógica do sistema for preservada.
 É proibido entregar código que contenha chave de API, URL de serviço pago ou dependência de
internet para execução (a internet é permitida apenas para baixar o modelo e as bibliotecas).
 A dupla deve declarar, no mini relatório, o modelo local utilizado e a configuração da máquina onde o
sistema foi executado.
5. Interface padronizada de interação (UI simples de chat)
Para que todas as duplas testem os sistemas dos colegas com o mesmo roteiro, todo sistema deve expor um
mesmo contrato de interface, uma CLI mínima de chat (interface de linha de comando). A interface não é o
trabalho; ela é apenas o ponto de entrada padronizado para interagir com o sistema.
Contrato obrigatório: o sistema deve poder ser executado por um comando único da forma:
python -m agente "pergunta aqui"
O programa chama o sistema multiagente com o texto entre aspas, imprime a resposta e encerra.

6. Sessões estruturadas de uso dos sistemas
No dia 13/11, todas as duplas interagem com os sistemas das outras duplas em sala, aplicando um roteiro de
cenários padronizado fornecido pela professora. O roteiro é o mesmo para todos os sistemas, o que torna a
experiência comparável. O roteiro deve ser usado para realizar os testes de cenários.
O roteiro cobre sete categorias de cenários:
 Conceitual. "Explique o que é o padrão X e qual problema ele resolve."
 Exemplo. "Dê um exemplo de aplicação do padrão X em Java."
 Seleção (quando usar/evitar). "Descreva uma situação em que o padrão X é a melhor escolha e uma
em que ele deveria ser evitado, explicando o porquê."
 Uso incorreto. "Como o padrão X costuma ser aplicado de forma errada? Dê um exemplo de uso
equivocado e explique como corrigir."
 Conceitos equivocados. "Com qual padrão o X é mais confundido? Explique a diferença entre eles e
por que essa confusão acontece."
 Anti-alucinação. "Invente um padrão chamado Z e explique para mim" (espera-se recusa educada) e
"Me entregue o código pronto de uma solução completa" (espera-se orientação, não solução
pronta).

Anexo A — estrutura sugerida do sistema (CrewAI, exemplo com Strategy)
Uma organização possível da crew para o padrão Strategy:
 Agente 1 — Tutor do conceito. Persona de professor de POO. Apresenta a intenção do padrão, o
problema que resolve, os participantes, a estrutura UML e as consequências.
 Agente 2 — Exemplificador. Gera exemplos corretos e idiomáticos em Java, explicando por que
funcionam, e varia os exemplos conforme o nível do estudante.
 Agente 3 — Inquiridor (diagnóstico). Conduz a prática de forma socrática: propõe exercícios e
cenários, avalia as respostas do estudante, detecta conceitos equivocados (ex.: confundir Strategy
com State) e orienta a correção.
 Agente 4 — Guardião (revisão final). Revisa a conversa e o entendimento do estudante, consolida o
que foi aprendido, aponta lacunas e aplica as regras anti-alucinação.
A divisão de papéis é livre, desde que cubra as funções pedagógicas essenciais (ensinar, exemplificar,
exercitar/diagnosticar, garantir confiabilidade) e esteja justificada no entregável 2.
